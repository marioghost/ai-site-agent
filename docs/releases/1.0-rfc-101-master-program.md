# 1. Program purpose

## 1.1 Why this document exists

The Master Inventory defines **what** must be completed. The Execution Strategy defines **how** work may proceed (ownership, moves, dependencies, forbidden work). Neither is an executable program of work packages.

This Master Program is the **single implementation authority** that:

- decomposes inventory clusters into implementation-sized work packages;
- binds each package to scope, inputs, outputs, dependencies, and acceptance boundaries;
- defines evidence, tracking, quality gates, risks, reopen policy, and program completion;
- makes future cluster implementation **mechanical**: each implementation plan and Step document derives from a package ID herein.

## 1.2 Relationship to other documents

| Document | Relationship |
|----------|--------------|
| **Master Inventory** | Scope source. This Program must not add, remove, or reprioritize inventory items. Packages map onto inventory findings/clusters. |
| **Execution Strategy** | Law. Packages must obey principles, rules, dependency edges, migration philosophy, and DoD. |
| **Implementation plans** (future) | Derive from one or more package IDs in §3. They may not invent scope outside packages. |
| **Step documents** (future) | Reference this Program + package IDs + Inventory findings + Strategy rules. They do not redefine architecture. |
| **RFC-101 / RFC-102 / Product Readiness** | Unchanged SoTs. Packages implement them; they do not rewrite them. |

## 1.3 What this Program is not

- Not a roadmap (no ordering mandate, no milestones, no dates).  
- Not implementation (no code).  
- Not architecture (no new IA, routes, or ownership).  
- Not prioritization (packages are peer organizational units).

# 4. Dependency execution graph

## 4.1 Dependency classes

| Class | Meaning |
|-------|---------|
| **Hard** | Dependent package cannot meet its acceptance boundary until the dependency’s outputs exist |
| **Soft** | Improves structure/safety; dependent may start in limited form; DoD may still require soft deps for full close |
| **Optional** | Improves quality; never blocks package acceptance boundary |

# 6. Acceptance workflow

Mandatory sequence for every work package (except G11-P0 boundary-only, which stops at Review → Accepted boundary record):

```
Review
  → Implementation
  → Tests
  → Product Readiness (Gate record if user-facing; N/A if pure tooling/docs with justified N/A)
  → Acceptance
  → Inventory closure (findings claimed by package)
  → Program completion update (cluster/package status)
```

| Stage | Required action |
|-------|-----------------|
| **Review** | Implementation plan cites package ID, Inventory findings, Strategy rules, boundaries |
| **Implementation** | Code/docs only within §5 boundaries |
| **Tests** | Automated tests green; ownership tests updated |
| **Product Readiness** | Gate ∈ {PASS, PASS WITH DEBT, N/A} per RFC-PRODUCT-READINESS; debt registered |
| **Acceptance** | Strategy §7–§8 / this Program §9 quality gates satisfied |
| **Inventory closure** | Claimed findings marked closed in program tracking (inventory history preserved) |
| **Program completion update** | Package status → Completed; cluster rollup updated (§8) |

Rejection at any stage returns status **Rejected** or **Reopened** per §11—not silent partial merge as Done.

# 11. Reopen policy

### 11.1 When reopen is allowed

A **Completed** package may be **Reopened** only if:

1. A defect proves acceptance boundary was false (duplicate owner, missing redirect, eng leak, failing Gate on claimed surface); or  
2. A later package discovers an incomplete move that the completed package claimed; or  
3. Inventory finding closed by the package must be corrected due to factual error.

### 11.2 When reopen is forbidden

- To invent features  
- To redesign RFC-101/102  
- To reprioritize or reshuffle program politics  
- To reopen RFC-100 / Step 067 / engineering closure  
- To “improve cosmetics only” without ownership/defect basis (handle as new package if inventory already covers; else out of scope)

### 11.3 Required evidence to reopen

- Defect description with surface/route evidence  
- Failed checklist item from §7/§9  
- Proposed delta still within original package scope (or new package ID if scope expands—expansion requires inventory coverage)

### 11.4 Approval requirements

- Product Completion owner review (architecture + product)  
- Gate re-run if user-facing  
- Status transitions: `Completed` → `Reopened` → (fix) → `In review` → `Accepted` → `Completed`  
- Inventory closure corrected (re-open finding then re-close with new evidence)

# 12. Program completion

RFC-101 Product Completion is **complete** only when all of the following are true—aligned with frozen authorities; **no new conditions invented**:

### From RFC-101

- Default product IA: Home · Knowledge · Ask · Insights · Settings (Mode off)  
- Engineering Mode exists, default off, Eng destinations per spec  
- Screen Contracts satisfied for product/eng screens in inventory scope  
- Terminology glossary applied; forbidden top-level module names retired  
- Legacy routes redirect per §12 for migrated surfaces  

### From RFC-102

- Migrated owners live under feature-module structure  
- Eng isolation structurally enforced  
- Shared patterns applied on migrated screens; no permanent legacy monolith owners for RFC-101 screens  

### From Execution Strategy Success Criteria

- Single ownership; no duplicate nav/UI for claimed jobs  
- Capabilities moved not deleted  
- Home readiness without Overview wall  
- Ask productized; diagnostics in Eng  
- Settings split; eng knobs not in default product Settings  
- RFC-100 engineering closure intact; ops gates unchanged by this program  

### From Product Readiness

- Program workstreams for Dashboard UX/IA/Design/Eng Mode/Simplicity/Validation satisfied for Accepted Product criteria  
- Gate discipline applied; no open **must resolve before Release 1.0 Acceptance** product debt remaining (per Product Readiness debt policy)  
- Cold-demo without coaching achievable on the product (Mode off)  

### From Master Inventory

- Findings claimed by G1–G10 and G12 closed in program tracking  
- G11 remains excluded from Dashboard completion (tracked separately)  
- Part B duplicate/overlap conflicts resolved in the product (not merely documented)  

### From this Program

- All in-scope packages **Completed**  
- Evidence indexes complete without mandatory duplication  
- No package left **Reopened** or **Rejected** without disposition  

When the above hold, Product Completion may declare **program complete**. That declaration is **Product Accepted Product** readiness per LIFECYCLE dual model—not a rewrite of Step 067 engineering closure.
