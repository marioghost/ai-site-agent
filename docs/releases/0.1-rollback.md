## Deployment procedure

### 1. Build & test

```bash
cd backend
.venv/bin/pytest tests/test_golden_chat_parity.py tests/test_legacy_guards.py \
  tests/test_chat_executive_routing.py tests/test_chat_stream_executive_routing.py \
  tests/test_executive_service.py -v -m unit
```

### 2. Deploy application

Deploy backend + dashboard as usual (no schema changes in 0.1).

**Environment variable (keep default for production first deploy):**

```bash
# Default — legacy path (safe)
KNOWLEDGE_OS_EXECUTIVE_ENABLED=false
```

Add to `.env` / deployment manifest. See `.env.example` comment block.

### 3. Post-deploy smoke (flag OFF)

```bash
# Health
curl -sS http://<host>:8000/api/health

# Auth + chat session (adjust credentials)
TOKEN=$(curl -sS -X POST http://<host>:8000/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":"<password>"}' | jq -r .access_token)
SID=$(curl -sS -X POST http://<host>:8000/api/chat/sessions \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{}' | jq -r .session_id)
curl -sS -X POST http://<host>:8000/api/chat \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d "{\"message\":\"What does the company do?\",\"session_id\":\"$SID\"}"
```

Confirm HTTP 200 and logs show `path=legacy`.

### 4. Staging shadow validation (flag ON)

**Staging only.** Do not enable in production until this section passes.

```bash
KNOWLEDGE_OS_EXECUTIVE_ENABLED=true
# restart backend
```

Repeat chat smoke. Confirm:

- [ ] HTTP 200 responses
- [ ] Logs show `path=executive` and `request_id` on dispatch
- [ ] Response schema unchanged (answer, sources, metadata keys)
- [ ] Golden unit suite still green on build artifact

Optional integration gate:

```bash
export POSTGRES_TEST_URL=postgresql+psycopg://...
export GOLDEN_CHAT_LIVE=1
cd backend && .venv/bin/pytest tests/test_golden_chat_parity.py -m integration -v
```

### 5. Performance baseline capture (staging)

Run **once per environment** with representative fixture site + LLM. Record in next release acceptance report.

Suggested script (adapt host/token):

```bash
# Non-streaming — 20 requests
for i in $(seq 1 20); do
  curl -sS -o /dev/null -w "%{time_total}\n" -X POST http://<host>:8000/api/chat \
    -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
    -d "{\"message\":\"What does the company do?\",\"session_id\":\"$SID\"}"
done | sort -n
# Compute P50/P95 manually or with awk

# Streaming — observe time_to_first_token_ms in SSE events
curl -N -X POST http://<host>:8000/api/chat/stream \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d "{\"message\":\"What does the company do?\",\"session_id\":\"$SID\"}"
```

Compare flag OFF vs ON on staging; Executive overhead should be negligible vs LLM/retrieval (see acceptance report mocked baseline).

### 6. Production rollout

**Release 0.1 recommendation:** ship with flag **OFF**. Enable Executive path in production only after staging shadow sign-off in a later change window.

## Rollback procedure

| Step | Action |
|------|--------|
| 1 | Set `KNOWLEDGE_OS_EXECUTIVE_ENABLED=false` or remove variable |
| 2 | Restart backend processes |
| 3 | Clear retrieval + answer caches if responses seem stale |
| 4 | Verify logs show `path=legacy` |
| 5 | Run golden unit smoke |
| 6 | Post-mortem if customer-facing impact |

**Rollback time:** minutes (config restart only; no DB rollback required).

---

## What this release does NOT change

- Retrieval pipeline logic (`RetrievalPipelineService` → `DocumentFirstRetrievalPipeline`)
- LLM prompts, polish, caches (when flag OFF, code path identical to pre-0.1)
- Dashboard UI
- Knowledge Profile API or presets
- Database schema
