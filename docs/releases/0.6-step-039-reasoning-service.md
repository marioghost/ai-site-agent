# Release 0.6 — Step 039: ReasoningService passthrough

**RFC-100 Step 039**  
**Lifecycle state:** Implementation → Engineering Ready (after review)

## Summary

Introduces `ReasoningService` as a **stateless passthrough facade** over the
current Rag answer path. Establishes reasoning ownership and a migration seam.
**Default flag OFF** — production behavior unchanged.

## Delivered

| Item | Path |
|------|------|
| Service | `backend/app/services/reasoning/` |
| Flag | `REASONING_SERVICE_ENABLED` (default false) |
| Wiring | `ExecutiveService`, `app.api.chat` dispatch |
| Marker | `reasoning_path` on `RagResult` / stream `final` |
| Tests | `backend/tests/test_reasoning_service.py` |
| Docs | `docs/REASONING_SERVICE.md` |

## Flag matrix

| Executive | Reasoning | Path |
|-----------|-----------|------|
| OFF | OFF | `RagService` (legacy — unchanged) |
| OFF | ON | `ReasoningService` → Rag |
| ON | OFF | `Executive` → Rag (unchanged) |
| ON | ON | `Executive` → `ReasoningService` → Rag |

## Non-goals (this step)

- No Epistemic Memory / tension consumption
- No retrieval / ranking / prompt / LLM / streaming protocol changes
- No answer text changes
- No Evidence Assembly or Language split yet
- Flag not default ON

## Performance

| Concern | Step 039 impact |
|---------|-----------------|
| Dispatch overhead | One extra Python call + thin wrapper when flag ON |
| Object allocation | One `ReasoningRequest`/`ReasoningResult` per turn when ON |
| Token impact | **None** — no extra LLM calls |
| External calls | **None** — no duplicate retrieval |
