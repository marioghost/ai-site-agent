# Release 0.5 — Step 037: Tension operational metrics

**RFC-100 Step 037**  
**Lifecycle state:** Implementation → Engineering Ready (after review)

## Summary

Read-only Prometheus / JSON gauges for Tension Surfacing hypothesis counts.
No detection-rule changes, no persistence, no maintenance, no chat/retrieval impact.

Semantics: gauges count **possible** epistemic issues (hypotheses), not confirmed
knowledge errors. Only `support_deficit` and explicit `conflict` are measured.

## Delivered

| Item | Path |
|------|------|
| Count API | `TensionSurfacingService.summarize_counts()` |
| Metrics service | `OperationalMetricsService` (+ tension gauges) |
| JSON schema | `OperationalMetricsResponse` (additive fields) |
| Tests | `tests/test_operational_metrics.py` |
| Docs | `docs/TENSION_SURFACING.md`, `docs/MEMORY_VERSION.md` |

## Gauges

| Prometheus name | JSON field |
|-----------------|------------|
| `kos_open_tensions` | `open_tensions` |
| `kos_support_deficit_tensions` | `support_deficit_tensions` |
| `kos_conflict_tensions` | `conflict_tensions` |

Also exported: `tension_claim_scan_limit` (JSON) documenting the scan bound.

Existing `kos_memory_version` / `kos_knowledge_version` unchanged in meaning.

## Boundaries

- Metrics → `TensionSurfacingService` only (no epistemic ORM in metrics layer)
- Bounded scan: `METRICS_CLAIM_SCAN_LIMIT` = 500 active claims
- Repeated scrapes do not mutate Epistemic Memory or `memory_version`
- Endpoints remain unauthenticated like `/api/health` (ops convention)

## Cost / scalability

Per scrape: ≤ `METRICS_CLAIM_SCAN_LIMIT` (500) active claims + evidence-link lists via Epistemic Memory service.
Not a full-corpus unbounded walk. Claims beyond the limit are not counted.

**Why 500:** engineering safety bound for operator scrapes — not a cognitive
limitation. Same ceiling as `DEFAULT_CLAIM_LIMIT` so metrics and detection agree.

## Explicit non-goals

- No new tension types
- No tension persistence
- No investigation / maintenance execution
- No detection-rule redesign
