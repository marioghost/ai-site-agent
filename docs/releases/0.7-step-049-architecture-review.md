## Executive summary

Step 049 is an **offline engineering evaluation gate**, not a runtime subsystem.

Its job is to measure, from **already-produced diagnostic DTOs**, how Memory Assist (047) and Canonical Shadow (048) relate to retrieval outcomes — so operators can decide whether Memory coverage is sufficient to consider **staging enablement** of assist (still default OFF; never “default ON in production” in this step).

**Preferred architecture:** an **Operations / Evaluation** package (script + report aggregator) that:

1. Replays or harvests turns under **controlled staging flags** (or consumes exported diagnostic fixtures),
2. Aggregates `MemoryAssistResult` + `MemoryCanonicalShadowResult` (+ corpus counters),
3. Emits a **versioned JSON report** and a human **markdown summary**,
4. Writes **nothing** into Epistemic Memory, Settings, cache, Qdrant, or answer paths,
5. Introduces **no new feature flag** and **no chat-path import**.

**Verdict:** **GO for implementation after approval**, with the boundaries below. Step 049 is **necessary but not sufficient** for Release 0.7 closure.

## 1. What Step 049 owns

### 1.1 Responsibilities

| Owns | Does not own |
|------|----------------|
| Offline evaluation harness / CLI entry | Chat request lifecycle |
| Aggregation of assist + shadow diagnostics across a query set | Memory region semantics |
| Coverage and divergence **reporting** | Divergence **comparison logic** (already Step 048) |
| Explicit GO / NO-GO recommendation fields for **staging assist enablement** | Enabling flags itself |
| Deterministic report schemas | Operator dashboards (optional consumer later) |

### 1.2 Boundaries

```
┌─────────────────────────────────────────────────────────┐
│  Step 049 — Offline Evaluation (Operations)             │
│                                                         │
│  Inputs: frozen diagnostic fixtures OR harvested        │
│          retrieval_debug / reasoning_diagnostics blobs  │
│                                                         │
│  Process: aggregate → scoreboard → report               │
│                                                         │
│  Outputs: JSON report + markdown summary (artifacts)    │
└─────────────────────────────────────────────────────────┘
         ▲ consumes DTOs only
         │ never calls
         ▼
   Reasoning (047/048 already produced diagnostics)
   Epistemic Memory / DFP / Rag / Language  ← FORBIDDEN as live deps in eval core
```

### 1.3 Inputs

**Primary (required for shadow/assist analysis):**

| Input | Source | Notes |
|-------|--------|-------|
| `MemoryAssistResult` or its `to_diagnostics()` dict | Step 047 | Path, counts, IDs, usable flag, corpus flags |
| `MemoryCanonicalShadowResult` or its `to_diagnostics()` dict | Step 048 | Alignment, divergence codes, ID set sizes |
| Query identity | Eval fixture | Query id / text hash — **not** answer text |
| Run metadata | Eval harness | `memory_version`, `knowledge_version`, flag snapshot, alembic head, git commit |

**Secondary (optional, for coverage gate — read-only DB counts, not chat):**

| Input | Source | Notes |
|-------|--------|-------|
| Corpus counters | Ops SQL / existing health endpoints | sources, chunks, claims, observations, evidence_links |
| Shadow-write Settings state | Settings row | Whether SI shadow write is ON in the evaluated environment |

**Explicitly not required as inputs to the aggregator core:**

- Raw `PipelineResult.hits` chunk text
- `RagResult.answer`
- Prompts
- Claim propositions

`PipelineResult` / `RagResult` may appear in a **harvest adapter** only as carriers of the diagnostic objects already attached; evaluation logic must key off assist/shadow DTOs (or their diagnostics dicts).

### 1.4 Outputs

| Output | Form | Persisted? |
|--------|------|------------|
| `MemoryAssistEvalReport` (name TBD) | Versioned JSON schema | **Artifact file** under `docs/releases/reports/` or `backend/reports/` — not a new DB table |
| Human summary | Markdown | Same — commit or CI artifact |
| Recommendation block | Enum: `NO_GO` / `CONDITIONAL` / `STAGING_CANDIDATE` | Inside report only |
| Per-query rows | Bounded ID lists + codes | Inside JSON; ID caps as in Step 048 |

**Must NEVER own:**

- Feature flags or Settings mutations
- Migrations
- Chat routing
- Retrieval / DFP / Qdrant
- `read_region()` as part of “evaluation scoring” (see §3)
- LLM calls
- Ranking, prompts, answers, cache namespaces
- Epistemic writes
- Redefinition of divergence codes (reuse Step 048 constants)

## 2. Runtime impact

| Surface | Step 049 executes? | Why |
|---------|-------------------|-----|
| Chat (stream / non-stream) | **No** | Violates snapshot invariants; would couple ops eval into Rag |
| Indexing / SI generation | **No** | Different concern; shadow write already gated |
| Deployment / migrate | **No** | No schema; no flag |
| CI (optional job) | **Yes, offline** | Deterministic fixtures / disposable DB |
| Engineer laptop / staging batch | **Yes, offline** | Primary intended use |

### Why offline only

1. **RFC-100 text:** “Offline eval script + report.”
2. **Snapshot invariant:** assist/shadow are diagnostic; eval must not become a second cognitive path.
3. **False confidence risk:** online eval mid-chat would mix cache hits, skipped shadows, and partial flags into “metrics.”
4. **Rollback:** an offline script can be deleted without touching production chat.

**Harvest mode (allowed):** a staging batch may run chat **with flags temporarily ON** solely to **collect** diagnostics, then feed frozen blobs into the offline aggregator. The chat path remains Steps 047–048; Step 049 still does not live inside `RagService` / `ReasoningService`.

## 3. Evaluation inputs — DTO sufficiency

### 3.1 Can evaluation operate without touching retrieval or Memory again?

**Yes — for divergence / assist behaviour analysis.**

The aggregator should accept a list of turn records shaped like:

```text
EvalTurnRecord
  query_id
  assist: MemoryAssistResult | diagnostics dict
  shadow: MemoryCanonicalShadowResult | diagnostics dict
  flags_effective: { reasoning, assist, cache_v2, shadow }
  cache_hit: bool
  versions: { knowledge_version, memory_version }
```

These fields are already produced when the coordinated pipeline runs with assist/shadow effective and no answer-cache hit.

### 3.2 When is a fresh `read_region()` or retrieval needed?

| Need | Allowed in Step 049? | How |
|------|----------------------|-----|
| Re-score shadow math | **No** — already in Step 048 | Consume shadow result |
| Measure “claims in DB” coverage | **Yes, read-only count** | Separate coverage probe (SQL/API), not Memory assist path |
| Re-run full chat to harvest | **Yes, as batch driver** | Uses existing Reasoning path; eval package does not embed Qdrant/DFP |

**Architectural rule:** the **evaluation core** (`aggregate` / `report`) must not import Qdrant, DFP, `EpistemicMemoryService`, or Rag. A thin **harvester CLI** may call existing chat/Reasoning APIs as a black box to produce fixtures — that is ops glue, not cognitive ownership.

### 3.3 DTO choice

| DTO | Role in Step 049 |
|-----|------------------|
| `MemoryAssistResult` | Assist path distribution, usable rate, empty/sparse rates |
| `MemoryCanonicalShadowResult` | Alignment + divergence code frequencies |
| Diagnostics dicts | Stable serialization for fixtures |
| `PipelineResult` / `RagResult` | Harvest carriers only — strip to diagnostics before aggregate |
| `MemoryRegionView` | **Out of scope** for aggregate core (contains claim text) |

1. **`memory_assist_eval_report.v1.json`**

|-------|----------|

### 5.3 Metrics object (inside report)

Aggregate counts and rates only — no free-text evidence.

## 6. Metrics

### 6.1 Meaningful metrics

| Metric | Why meaningful |
|--------|----------------|
| **Assist path histogram** (`off`/`skipped`/`used`/`empty`/`sparse`/`failed`) | Shows whether assist actually ran |
| **Effective-flag rate** | Separates “flag off” from “Memory empty” |
| **Empty-memory rate** (among attempted) | Coverage / gate signal |
| **Sparse-memory rate** | Expected early; not a quality score |
| **`usable_for_evidence` rate** | Assist contract health |
| **Corpus configured rate** | Fail-closed boundary working? |
| **Shadow path histogram** | Compared vs skipped vs empty_memory |
| **Canonical alignment histogram** (`aligned`/`partial`/`divergent`/`not_evaluable`) | Descriptive overlap only |
| **Divergence code frequency** | Engineering signal for systematic gaps |
| **Overlap / memory-only / retrieval-only counts** (means + percentiles) | Set geometry — not “accuracy” |
| **Support-missing-from-context rate** | Uses support-specific semantics from cleanup |
| **Answer-cache-hit rate in harvest** | Explains missing shadow rows |
| **Corpus counts** (claims, observations, evidence_links, memory_version) | Coverage gate (~sparse today) |
| **Comparison duration_ms** (p50/p95) | Prove shadow stays cheap |

### 6.2 Misleading metrics — must NOT exist (or must be labeled forbidden)

| Anti-metric | Why forbidden |
|-------------|----------------|
| “Memory accuracy %” / “canonical correctness %” | Shadow does not decide truth |
| “Assist improved answer quality” | Step 047/048 do not change answers |
| LLM judge scores | Out of scope; couples Language |
| Embedding similarity between Memory and chunks | Second retrieval engine smell |
| Unbounded URL / proposition dumps | Violates diagnostics contract |
| Treating `retrieval_source_not_in_memory` as a bug | Expected while Memory is sparse |
| Ranking “winner” between Memory and DFP | Explicitly banned by Step 048 |

**Rule:** every reported number must be labeled **descriptive** or **coverage**, never **quality/accuracy**.

## 7. Placement

### Options considered

| Option | Pros | Cons |
|--------|------|------|
| **A. Inside Reasoning package** | Near DTOs | Pollutes cognitive layer with ops; import temptation into chat |
| **B. Operations / Evaluation package (preferred)** | Matches RFC “offline eval”; clear boundary | Needs thin import of DTO types only |
| **C. Epistemic Memory package** | Near corpus | Wrong owner — Memory must not evaluate chat retrieval |
| **D. RagService hooks** | Easy harvest | Violates offline / God-Service shrink goals |

### Preferred ownership

**Operations / Evaluation**, e.g.:

```text
backend/app/services/evaluation/   # or backend/scripts/evaluation/
  memory_assist_eval_types.py      # report DTOs
  memory_assist_eval_aggregator.py # pure aggregation
  memory_assist_eval_report.py     # JSON/MD writers
backend/scripts/run_memory_assist_eval.py  # CLI entry
```

**Reasoning** remains the producer of assist/shadow diagnostics.  
**Evaluation** remains the consumer and reporter.

Reasoning may export DTO types; Evaluation must not be imported by Reasoning, Rag, EA, Language, or Memory.

## 8. Runtime boundaries vs Architecture Snapshot invariants

| Snapshot invariant | Step 049 preservation |
|--------------------|------------------------|
| Retrieval / DFP ≤ 1 per uncached chat turn | Eval core adds **0**; harvest uses existing path only |
| Memory read ≤ 1 per assist-effective turn | Eval core adds **0** |
| LLM ≤ 1 | Eval core adds **0** |
| No prompt influence | No Language / prompt imports in eval core |
| No ranking influence | No DFP / CanonicalSourceService calls |
| No cache influence | No namespace / cache store APIs |
| No answer influence | No Rag answer mutation |
| Shadow never changes answers | Eval only reads shadow diagnostics |
| Flags OFF = legacy | Step 049 adds **no flag**; chat unchanged |
| Memory never mutates on chat | Eval does not write Memory |

**Conclusion:** Step 049, as designed, **preserves all listed invariants**. Any implementation that adds chat imports or live Memory scoring is **out of architecture**.

**No.**

Per reconciled RFC numbering in the baseline:

| Step | Role relative to 0.7 |
|------|----------------------|
| 046–048 | Implemented seams |
| **049** | Offline eval **gate evidence** for staging assist candidacy |
| **050** | Release 0.7 engineering closure |

After Step 049, remaining for 0.7 closure typically includes:

1. Accepted eval report with explicit recommendation (likely **NO_GO** or **CONDITIONAL** while claims remain sparse).
2. Operator sign-off that staging assist remains OFF unless CONDITIONAL criteria met.
3. Closure documentation / build metadata update (Step 050).
4. Confirmation golden parity still green with flags OFF (unchanged expectation).

Step 049 **does not**:

- Close Release 0.7 by itself
- Authorize production assist ON
- Replace staging validation (`staging_validated` stays false until real staging work)

## 11. Risks

| Risk | Mitigation |
|------|------------|
| **False confidence** — high overlap on tiny claim set | Recommendation requires minimum claim/observation thresholds |
| **Metric abuse** — “accuracy” language in reports | Forbidden metrics list; review checklist |
| **Diagnostics as truth** — treating divergence as Memory “wrong” | Report copy: descriptive only; retrieval is authoritative today |
| **Future coupling** — eval imported into Reasoning | Boundary tests; package placement |
| **Second retrieval engine** — eval re-queries Qdrant to “verify” | Forbidden in eval core |
| **Harvest pollution** — answers/prompts in fixtures | Stripper that keeps only assist/shadow diagnostics + ids |
| **Cache-hit blind spot** — undercounting shadow | Explicit cache_hit dimension in report |
| **Sparse Memory misread as “aligned”** | Empty/sparse rates dominate recommendation until coverage gate |

## 12. Recommendation

### Preferred architecture

**Offline Operations/Evaluation aggregator + CLI**, consuming Step 047/048 diagnostic DTOs (or their `to_diagnostics()` forms), emitting versioned **JSON + markdown** reports, with **no new flag, no migration, no chat-path code**, and a **coverage-aware recommendation** that defaults to **NO_GO** until corpus thresholds are met.

### Why this beats alternatives

| Alternative | Rejected because |
|-------------|------------------|
| Inline Reasoning “eval phase” | Violates offline RFC intent; expands God-path |
| Live Memory re-read in eval | Duplicates assist; risk of second Memory engine |
| LLM-as-judge quality report | Out of scope; answer influence smell |
| New Settings flag for “eval mode” | Unnecessary; offline script suffices |
| Persisted eval tables | Premature; artifacts are enough for 0.7 gate |

### Implementation readiness

| Item | Status |
|------|--------|
| Architecture | **Ready for approval** |
| Implementation | **Blocked until this review is accepted** |
| Step 050 | **Do not start** |
| Runtime flags | **Remain default OFF** |

### Suggested acceptance criteria (for later implementation PR — not this review)

1. Eval core has zero retrieval/Memory/LLM imports.
2. Report generated from fixtures in CI.
3. Recommendation enum present; sparse corpus → `NO_GO` or `CONDITIONAL` with reasons.
4. `make release-check` / golden parity unchanged.
5. No migrations, no new Settings columns, no chat diffs beyond optional ignored scripts path.

## Appendix A — Suggested recommendation rules (non-normative until implementation)

Illustrative only; exact thresholds to be fixed in the implementation prompt after approval:

- `NO_GO` if `claims < coverage_min` OR `usable_for_evidence_rate == 0` on attempted turns OR corpus unconfigured.
- `CONDITIONAL` if coverage_min met but high empty/sparse rates or dominant `retrieval_source_not_in_memory`.
- `STAGING_CANDIDATE` only if coverage gate + assist effective rate + operational review checklist pass — **still not production default ON**.
