# Release 0.8 — Rollback procedures

**RFC-100 Release 0.8** (Steps 052–057)  
**Default runtime intent:** `allow_legacy_kp_presets=false`, `legacy_doc_type_canonical_enabled=false`; Memory assist/shadow **OFF**

**Public operator entry point:** `bash deploy/manage_deploy.sh <command>`  
Syntax source of truth: `bash deploy/manage_deploy.sh help`

Prefer least-disruptive rollback first. **Do not** use `ai_site_agent_recovery` as a feature rollback target. **Do not** clear Qdrant. **Do not** reindex merely to roll back 0.8 behavior. **Do not** use emergency deploy overrides for routine Release 0.8 rollback.

---

## Level 1 — Settings flags (preferred)

### Restore industry Knowledge Profile preset APIs

```text
allow_legacy_kp_presets = true
```

**When:** Operators need GET/POST `/api/knowledge-profile/presets` after Step 054 default-off.  
**Effect:** Preset list/load return prior 200 behavior (plus existing deprecation headers on load).  
**Database:** Column must exist (migration **0018** applied). Restart not required.

### Restore pre-055 doc-type canonical reorder

```text
legacy_doc_type_canonical_enabled = true
```

**When:** Overview/news quality regresses under default-off Step 055 path (news may outrank about/homepage).  
**Effect:** RPS finalize runs legacy `CanonicalSourceService` doc-type reorder again (subject to `enable_canonical_source_selection`).  
**Database:** Column must exist (migration **0019** applied). Restart not required.  
**Note:** This does **not** implement Memory authority.

### Combined Level 1

Set both flags `true` if both admin preset access and pre-055 reorder are required.

After Level 1, optionally confirm process identity (no redeploy required):

```bash
bash deploy/manage_deploy.sh status
bash deploy/manage_deploy.sh build-info
bash deploy/manage_deploy.sh health
```

## Level 2 — Code rollback (known-good `origin/main`)

`deploy/manage_deploy.sh` **does not** accept an arbitrary prior commit as a deploy argument. Release deploy always builds a **clean worktree from `origin/main`**.

Therefore Level 2 means: put the **known-good commit on `origin/main`**, then run the canonical deploy chain.

### 1. Exact rollback target

Choose one accepted tip, for example:

| Target class | Example tip (fill at execution) |
|--------------|----------------------------------|
| Last Release **0.7** accepted tip (pre-052) | record full SHA before cutover |
| Last known-good interim 0.8 tip before the regressing change | record full SHA |

Preferred git path: an approved **revert merge** (or equivalent) so `origin/main` advances to restore prior behaviour **without** force-push. Do **not** deploy from feature branches, dirty trees, or local-only commits.

### 2. Status check (diagnostic)

```bash
bash deploy/manage_deploy.sh status
```

Confirm: local `main` == `origin/main` == **rollback target SHA**; working tree **clean**.

### 3. Canonical deploy (one command)

```bash
sudo bash deploy/manage_deploy.sh deploy full
```

`deploy full` owns backup, migration decision/schema-first, sync, post-sync migrate, restart, health, verify-release, smoke, and the deployment report.

### 4. Optional diagnostics

```bash
bash deploy/manage_deploy.sh verify-release
bash deploy/manage_deploy.sh build-info
bash deploy/manage_deploy.sh smoke
```

### 5. Confirm runtime commit equals rollback target

From `deployments/latest.json` / optional `status` / `verify-release` / `GET /api/build`: runtime identity commit must equal the chosen rollback target SHA. If it does not match, **stop** — do not declare rollback complete.

**Effect:** Restores prior API/UI/retrieval gate code.  
**Does not** automatically drop Alembic columns if 0018/0019 were already applied (usually harmless; Level 1 flags restore 054/055 behaviour).

---

## Level 3 — Schema rollback (ops exception only)

Downgrade Alembic **only** under explicit ops approval. Prefer `bash deploy/manage_deploy.sh` operational paths; do not improvise one-off scripts.

Normally **unnecessary**: Level 1 flags restore 054/055 runtime behavior when columns exist.  
Never “fix” ranking by deleting Qdrant points or wiping corpus tables.

---

## Explicit non-actions

| Action | Allowed for 0.8 feature rollback? |
|--------|-----------------------------------|
| Toggle Settings flags | **Yes** (Level 1) |
| Redeploy known-good `origin/main` via `deploy full` | **Yes** (Level 2) |
| Deploy dirty / feature / local-only commits | **No** |
| Emergency deploy overrides | **No** (routine rollback) |
| Use `ai_site_agent_recovery` | **No** |
| Clear / recreate Qdrant collections | **No** |
| Full reindex solely to undo 0.8 | **No** |
| Enable Memory Assist/Shadow as “fix” | **No** (separate experiment) |

---

## Verification after rollback

1. Confirm `deploy full` printed `VERDICT: SUCCESS` and `deployments/latest.json` `outcome=success`  
2. Optional: `bash deploy/manage_deploy.sh health` / `build-info` / `verify-release`  
3. Confirm Settings flag values  
4. Confirm corpus and Qdrant counts unchanged
