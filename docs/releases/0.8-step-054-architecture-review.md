## 1. Inventory — current preset surface

### 1.1 Flag existence

**PROVEN BY CURRENT CODE:** `allow_legacy_kp_presets` does **not** exist in `backend/`.

Hits are documentation only (`FEATURE_FLAGS.md` “Planned flags”, RFC-100, Release 0.2 acceptance note).

Step 054 therefore must **introduce** the flag **and** ship it with **default false** (RFC Step title). The older MIG wording “default true → false in 0.8” described a transition that never landed as code; at 0.8 Step 054 the end state is **false**.

### 1.2 Industry presets (`PRESETS`)

**PROVEN BY CURRENT CODE** — `backend/app/services/knowledge_profile_service.py` (~483–491, ~957–973):

| `preset_id` | Role |
|-------------|------|
| `generic_corporate` | Safe default / empty-JSON fallback |
| `bank_financial` | Industry template (highest architectural debt — TD-01) |
| `ecommerce` | Industry template |
| `saas` | Industry template |
| `documentation_portal` | Industry template |
| `government` | Industry template |
| `university` | Industry template |

- `load_preset(name)` → `deepcopy` or `KeyError`
- `list_presets()` → all keys with labels
- `default_profile()` / `from_settings()` empty JSON → **`generic_corporate`**

### 1.3 HTTP API today

**PROVEN BY CURRENT CODE** — `backend/app/api/knowledge_profile.py`:

| Endpoint | Auth | Today | Deprecation |
|----------|------|-------|-------------|
| `GET /api/knowledge-profile/presets` | authenticated | **200** full list | none |
| `POST /api/knowledge-profile/presets/load` | admin | **200** persist + cache invalidate + reprocess mark; unknown id **404**; invalid **422** | `Deprecation: true` + `Link` via `knowledge_profile_deprecation.py` (Step 017) |

**Not implemented:** HTTP **410** for disabled presets.

Unrelated KP endpoints (GET/PUT profile, import/export) stay available and are **not** the Step 054 gate.

### 1.4 Dashboard

**PROVEN BY CURRENT CODE:**

- `KnowledgeProfilePage.tsx` lists presets and calls `POST .../presets/load`
- `KnowledgeProfileLegacyBanner.tsx` — info banner already present (MIG “UI banner” partially satisfied)
- Client does not yet handle **410**

Agent Settings presets (`automatic` / `fast` / …) are **out of scope** (different system; Step 053 cleaned boost pollution there).

### 1.5 Generation / wizard (related, not the RFC title)

**PROVEN BY CURRENT CODE:**

- `structure_analyzer.py` classifies sites into preset ids (incl. `bank_financial`)
- `profile_assembler.py` seeds from `PRESETS.get(preset_id, generic_corporate_profile())`
- Apply path: `POST /api/knowledge-profile/generate/...` (separate router)

This path can **reintroduce industry templates without** calling `/presets/load`. Treating generation as in-scope expands Step 054 beyond “Preset API / Preset 410” unless explicitly approved.

### 1.6 Tests / golden

**PROVEN BY CURRENT CODE:** unit tests import `PRESETS[...]` directly (including `bank_financial`). Golden fixture uses `fixture_profile: "generic_corporate"`. Step **056** later restricts CI golden to generic — **not** Step 054.

### 1.7 Flag storage pattern to mirror

**PROVEN BY CURRENT CODE** — Settings-backed bools (`memory_*_enabled`):

1. Alembic `add_column` + `server_default`
2. ORM `Mapped[bool]`
3. Pydantic Settings schema GET/PUT
4. `feature_flags.py` helper reading `getattr(settings, …)`
5. Docs in `FEATURE_FLAGS.md`

Env-only flags (`REASONING_SERVICE_ENABLED`, etc.) are a poorer fit for ops rollback of a Settings admin surface.

## 5. Options

| Option | Description | Risk | Recommend? |
|--------|-------------|------|------------|
| **A. Load-only 410** | Flag default false; only `POST /presets/load` → 410; `GET /presets` still lists | Operators see presets they cannot load; incomplete vs MIG “API returns 410” | **No** |
| **B. List + load 410** | Flag default false; both preset endpoints → **410** when false; Settings exposure; migration; dashboard handles 410; banner update; keep `PRESETS` for tests/generation | Low ranking risk; clear admin contract; matches RFC detail | **Yes** |
| **C. Soft list** | Load → 410; list returns only `generic_corporate` when false | Ambiguous “legacy” boundary; still allows generic load via API | **REQUIRES ADR** |
| **D. B + gate generation** | Also block industry seeding in generate/assembler when flag false | Larger blast radius; may surprise wizard users; not in Step title | **No for 054** — **DEFERRED** |
| **E. Delete presets / rewrite live profiles** | Remove industry builders; force generic in DB | High; ranking/ops risk; not rollback-friendly | **Forbidden** |
| **F. Env-only flag** | No Settings column | Poor ops rollback vs RFC “Flag true” | **No** |

### Recommendation

**Option B** — **PROPOSED MINIMAL INTERPRETATION** that satisfies:

1. RFC title — introduce `allow_legacy_kp_presets` with **default false**  
2. RFC detail — **Preset 410** on the preset API  
3. MIG-013 — 410 + UI warning/banner; rollback flag true  
4. No chat/ranking/Memory/Reasoning/Qdrant changes  
5. No Step 055/056 scope creep  
6. No deletion of in-process `PRESETS` (tests + deferred generation)

### Open decision (non-blocking if Option B chosen)

Whether `generic_corporate` should remain loadable when the flag is false is **Option C**. Default recommendation is **B** (all preset HTTP endpoints 410) because:

- `generic_corporate` remains the **automatic** empty-JSON default without needing HTTP load  
- Operators retain PUT/import for intentional profile edits  
- “allow_legacy_kp_presets” reads as a gate on the **legacy preset API**, not a partial industry filter  

If product wants an escape-hatch load of generic only → approve **Option C** explicitly (**REQUIRES ADR**).

## 6. Proposed implementation sketch (not executed)

1. **Alembic** `0018_allow_legacy_kp_presets` (next free revision after `0017_…`):  
   `settings.allow_legacy_kp_presets BOOLEAN NOT NULL DEFAULT false` (server_default false).
2. **ORM** + **SettingsRead/Update** + `_to_read` / `update_settings` mapping.
3. **`feature_flags.allow_legacy_kp_presets(settings) -> bool`**.
4. **API guards** at start of `list_presets` and `load_preset`:  
   if not allowed → `HTTPException(410, detail=…)` (stable machine-readable detail string).  
   When allowed → preserve today’s 200 + Deprecation headers on load.
5. **Dashboard:** handle 410 on list/load; keep/strengthen legacy banner; do not crash Settings/KP page.
6. **Tests:** unit/API — flag false → 410; flag true → 200; ranking/golden unchanged; no cache NS change.
7. **Docs:** `FEATURE_FLAGS.md` implement section; brief implementation note after coding.

**Explicit non-goals in sketch:** delete `PRESETS`; change generation; change DocumentScorer/RPS; enable any other flags; deploy; mutate live `knowledge_profile_json`.
