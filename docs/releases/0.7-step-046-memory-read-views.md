# Release 0.7 — Step 046: Memory read views (claims by region)

**RFC-100 Step 046**  
**Lifecycle state:** Implemented — dual-scope isolation extension

## Summary

Adds an **internal, read-only** typed facade:

```
MemoryRegionRequest → EpistemicMemoryService.read_region() → MemoryRegionView
```

Region is a **bounded filter lens** over existing claims — not a persisted entity, taxonomy, or ranking engine.

**No chat behavior change.** No feature flag. No HTTP route.

## Dual-scope model

| Layer | Purpose | Fields |
|-------|---------|--------|
| **Isolation scope** | Which deployment corpus may be read | `MemoryIsolationScope`: exactly one of `corpus_scope=DEPLOYMENT` or `source_ids` |
| **Cognitive filters** | Which claims inside that corpus match the request | `topic_key`, `page_roles`, `document_types`, `proposal_kinds`, provenance, lifecycle, pagination |

Legacy `source_id` / `source_ids` on `MemoryRegionRequest` remain for compatibility; internally normalized to `MemoryIsolationScope(source_ids=…)`.

### Deployment corpus scope (`MemoryCorpusScope.DEPLOYMENT`)

Boundary resolved in `memory_corpus_resolver.py` from the **canonical Settings row** (`SettingsRepository.get()` — lowest `id`):

1. `settings.allowed_domains_json` (normalized lowercase hosts)
2. Fallback: host from `settings.site_url`

**Fail-closed:** unconfigured boundary → empty region, `corpus_scope_unconfigured`, **no global read**.

SQL isolation path: `EpistemicClaim → EvidenceLink → ObservationRef.source_id → Source.url` host match. `scope_json` is **not** used for isolation.

Subdomain semantics reuse `is_allowed_domain()` (crawler-aligned).

No arbitrary source truncation in queries; `corpus_anchor_source_ids` in the view is diagnostic-only (cap 200).

### Explicit source scope

Positive `source_id` / `source_ids` for tests, source-detail tools, and engineering diagnostics. Behavior unchanged from initial Step 046.

## Corpus metadata (`MemoryRegionView`)

| Field | Meaning |
|-------|---------|
| `isolation_scope_echo` | Normalized isolation used for the read |
| `corpus_scope` | `DEPLOYMENT` when corpus isolation was requested |
| `corpus_hosts` | Normalized deployment hosts from Settings |
| `corpus_anchor_source_count` | Full count of Source rows matching boundary |
| `corpus_anchor_source_ids` | Diagnostic subset (bounded) of matching source IDs |
| `corpus_scope_configured` | Valid deployment host boundary was resolved |
| `corpus_scope_complete` | Full eligible source set evaluated (not truncated) |
| `corpus_limitations` | `corpus_scope_unconfigured`, `corpus_scope_invalid`, `corpus_scope_empty`, `corpus_scope_incomplete` |

`corpus_scope_complete` is **not** epistemic completeness — `completeness_unknown` remains `true`.

`corpus_boundary_fingerprint()` prepares Step 047 cache identity (hosts + boundary version).

## Evidence semantics (`MemoryClaimView`)

| Field | `include_evidence=True` | `include_evidence=False` |
|-------|-------------------------|--------------------------|
| `evidence_loaded` | `true` | `false` |
| `evidence` | loaded refs | `()` |
| `has_support` | `true` / `false` | `null` — **not interpretable** |
| `has_conflict` | `true` / `false` | `null` — **not interpretable** |

Region-level `evidence_not_requested` limitation is also set when evidence was not loaded.

**Step 047 obligation:** check `evidence_loaded` (or `evidence_not_requested` in limitations) before interpreting support/conflict booleans.

## Lifecycle truth table

| `active_only` | `include_superseded` | Result |
|---------------|----------------------|--------|
| `true` | `false` | Active claims only (superseded excluded) |
| `true` | `true` | All claims including superseded |
| `false` | `true` | All claims including superseded |
| `false` | `false` | **`ValueError`** — ambiguous; rejected before SQL |

## Query counts

| Path | `session.scalars` | `session.execute` (evidence) |
|------|-------------------|------------------------------|
| Explicit `source_ids`, no claims | 1 | 0 |
| `DEPLOYMENT`, configured, no matching sources | 1 | 0 |
| `DEPLOYMENT`, configured, with claims | 2 (source IDs + claims) | 0 or 1 |
| `DEPLOYMENT`, unconfigured | 0 | 0 |

Evidence load: one batched query when `include_evidence=True` and page has claims.
