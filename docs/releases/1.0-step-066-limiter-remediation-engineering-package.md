# 4. Root cause (frozen)

**LOCKED DECISION — root cause:**

The current limiter **violates the global concurrency invariant** because `ConcurrencyManager.configure()` creates **new** `threading.Semaphore` instances while concurrent requests may still hold **previous** instances.

| Fact | Class |
|------|--------|
| Every `/api/chat` (and stream) calls `_load_settings_and_configure()` → `configure()` before `chat_slot()` | **PROVEN** |
| `configure()` unconditionally assigns new `Semaphore(...)` for chat, LLM, embed, and background pools | **PROVEN** |
| `_Slot` captures the semaphore object at `*_slot()` call time; release returns to that object | **PROVEN** |
| `configure()` and `chat_slot()` are not atomic; lock covers only configure assignment | **PROVEN** |
| Multiple live generations ⇒ independent permit pools ⇒ aggregate holders can exceed configured limit | **PROVEN** |
| Waiters on an orphaned generation can time out while a newer generation has free capacity | **PROVEN** (interleaving) |
| Diagnostic `24×200` / `0×429` sole cause (fast completion vs race) | **NOT VERIFIED** for the specific run |

**LOCKED DECISION — nature of defect:** The defect is **architectural** (admission accounting). It is **not** solely a load-harness issue. Weak stimulus may also prevent 429 under a *correct* limiter; that does **not** excuse generation inflation.

**LOCKED DECISION — primary remediation target:** Restore process-wide enforcement of configured concurrency maxima for chat, LLM, and embedding limiters without capacity inflation under concurrent `configure` / acquire.

# 5. Global invariant (frozen)

**LOCKED DECISION — global invariant:**

At every instant, for each limiter kind (chat, interactive LLM, interactive embedding, and each background pool as defined by current APIs):

```text
active holders  ≤  configured limit
```

must hold **process-wide**.

Never “per semaphore generation.”

| Kind | Configured limit source (defaults) |
|------|-------------------------------------|
| Chat | `max_concurrent_chat_requests` (default **20**) |
| Interactive LLM | `max_concurrent_llm_requests` (default **2**) |
| Interactive embedding | `max_concurrent_embedding_requests` (default **2**) |
| Background embedding / background LLM reservation | Existing settings fields / derived `N-1` reservation — same invariant |

**LOCKED DECISION:** Observability counters that claim “active” must not contradict this invariant under correct implementation. Counters may temporarily exist for proof; they must not be used to justify exceeding the limit.

# 7. Dynamic settings (frozen)

**LOCKED DECISION:** Dynamic settings **remain supported**. Admin-mutable `max_concurrent_*` fields continue to exist. Changing settings **must not** create additional concurrent capacity beyond the newly configured process-wide limit.

## 7.1 Limits unchanged

**LOCKED DECISION:** When loaded settings equal the currently applied limits:

- Admission domain must **not** be recreated.  
- In-flight holders and free capacity must be undisturbed.  
- Effective capacity must remain exactly the configured limit (no reset to a fresh full pool alongside existing holders).

## 7.2 Limits increased

**LOCKED DECISION:** When a limit increases from \(L\) to \(L'\):

- Process-wide maximum holders becomes \(L'\).  
- Additional capacity may become available **only** as \(L' - L\) new admissions above current holders, never as “full \(L'\) on a new generation + existing holders on an old generation.”  
- Existing holders continue under the single admission domain.

## 7.3 Limits decreased

**LOCKED DECISION:** When a limit decreases from \(L\) to \(L'\):

- New acquisitions must not raise process-wide holders above \(L'\).  
- Existing holders **above** \(L'\) may complete naturally (no forced kill required by this package).  
- Until holders drain to \(\le L'\), new admissions are refused or wait per existing wait/overload semantics — **without** opening a parallel generation with a fresh \(L'\) permits on top of over-limit holders.  
- After drain, steady state respects \(L'\`.

## 7.4 Application path

**LOCKED DECISION — intent:** Settings may be read on the Ask path for other reasons, but **limiter apply** must obey §7.1–7.3. Unconditional per-request recreation is forbidden (§6). Preferred apply triggers are defined by the preferred architecture (§8), not by “configure every chat.”

# 8. Acceptable implementation shapes (evaluate only; freeze preferred)

This section evaluates shapes. It does **not** prescribe source code.

| Shape | Global-limit correctness | Dynamic updates | Complexity | Risk | Verdict |
|-------|--------------------------|-----------------|------------|------|---------|
| No-op configure when limits equal | Necessary; not sufficient alone if change still replaces with full new pool under load | Partial | Low | Low | **Required ingredient** |
| Configure-on-change only (still replace Semaphore with full new capacity) | Fails under concurrent holders at change time | Immediate but unsafe | Low | Med–High | **Reject as sole design** |
| Startup-only configure | Strong if no later replace | Loses live admin apply unless paired with safe update API | Low | Product gap if alone | **Reject as sole design** |
| Custom limiter (counter / permit accounting, single domain) | Strong | Can implement §7.1–7.3 | Medium | Medium | **Preferred core** |
| Condition-based limiter (`Condition` / event + counter) | Strong | Same as custom | Medium | Medium | **Acceptable equivalent** to custom |
| Generation migration (drain / hand-off across gens) | Possible if rigorously specified | Complex | High | High | **Reject** unless custom/condition proven impossible |

**LOCKED DECISION — preferred architecture:**

1. **Single admission domain** per limiter kind (one logical gate, not replaceable generations under concurrency).  
2. **No-op** when applied limits are unchanged.  
3. **Custom or condition-based limiter** (not raw `threading.Semaphore` replacement) that can raise/lower the target per §7 without allocating independent full capacity beside existing holders.  
4. Preserve existing public slot APIs’ behavioral contracts: `chat_slot` / `llm_slot` / `embed_slot` / background variants, `OverloadedError` on timed wait failure, blocking background slots as today.  
5. Hot-path Ask may read settings; it must **not** recreate limiters unsafely.

**LOCKED DECISION — rejected as unacceptable primary designs:** unconditional per-request Semaphore replacement; configure-on-change that still inflates via full new Semaphore under load; generation-migration as the default approach; startup-only if it removes dynamic settings without a safe update path.

## 12.2 Overload proof methodology

**LOCKED DECISION — occupancy model (not “just raise concurrency”):**

1. Guarantee **N** chat slots are **held** (N = configured chat limit).  
2. Admit additional requests that must wait longer than the chat wait window (**2.0s**).  
3. Exercise the **429** / `OverloadedError` path at least once under controlled burst.  
4. Confirm successful recovery afterward (subsequent Asks succeed; health OK).  
5. Confirm **no** QueuePool / unexpected 5xx collapse attributable to this amendment.  
6. Confirm no production-only test hooks remain enabled unintentionally.

Layers:

| Layer | Purpose |
|-------|---------|
| Unit/integration | Prove T5–T6 and global invariant without full site load |
| Runtime diagnostic | Prove overload mapping on deployed tip with occupancy model |
| Full 1-hour | Parent load acceptance after diagnostic PASS |
