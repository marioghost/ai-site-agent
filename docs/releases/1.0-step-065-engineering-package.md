# 2. Hybrid Registry Definition

**LOCKED DECISION — definition:**

The **hybrid flag registry** is the overlapping set of flag definitions, defaults, descriptions, inventories, and UI catalogs currently duplicated across:

1. environment configuration (`AppConfig` / env vars);  
2. Settings ORM / schema / database defaults;  
3. `backend/app/services/feature_flags.py` runtime helpers;  
4. build-info capability tuples and prose (`build_info_service._ENV_CAPABILITIES` / `_SETTINGS_CAPABILITIES`);  
5. `docs/FEATURE_FLAGS.md`;  
6. Dashboard migration / KOS flag catalogs (`MigrationFlagsPanel`, Overview KOS flag tags, similar lists);  
7. test matrices and confidence harnesses;  
8. maintenance-specific direct environment parsing (`maintenance_orchestration`).

It is **hybrid** because multiple surfaces independently describe or infer the same effective capability state, and some flags use different evaluation and observation paths.

**LOCKED DECISION:** Step 065 removes **duplicate registry ownership** (definition / observation / product exposure). It does **not** remove legitimate storage or runtime controls.

# 4. Canonical Ownership Contract

**LOCKED DECISION — ownership flow:**

```text
Environment / Settings storage
        ↓
canonical flag definitions + effective-value resolvers
        ↓
runtime consumers
        ↓
build-info observation (derived)
        ↓
Engineering Mode observation (when present) / ops via /api/build
        ↓
FEATURE_FLAGS documentation
```

### Storage ownership

| Surface | Owns |
|---------|------|
| **Environment** | Emergency kill-switches; infrastructure controls; `MAINTENANCE_EXECUTION_ENABLED`; `MAINTENANCE_INVESTIGATIONS_PER_CYCLE` |
| **Settings** | Durable capabilities: diagnostics v2, cache namespace v2, memory shadow/assist/canonical; legacy Settings-backed switches |

### Effective-value ownership

**LOCKED DECISION:** `feature_flags.py` (and existing capability-specific helpers therein) are the **canonical effective-value owners** for all flags that already have helpers.

- No runtime consumer may independently duplicate default parsing when a canonical helper exists.  
- **Maintenance:** parsing may remain in `maintenance_orchestration` (**LOCKED preferred**) with **one** declared owner and **one** registry/observation definition. Moving behind a helper is allowed only if contract-equivalent and fully regression-tested — prefer minimal normalization.

### Observation ownership

**LOCKED DECISION:** Build-info **derives** observation from canonical definitions/helpers + storage. It must **not** remain a second hand-written source of runtime **semantics** (effect text, defaults, active meaning).

### Product ownership

**LOCKED DECISION:** Default Product Settings must **not** expose the migration flag catalog. Engineering Mode is the only Dashboard home for raw/effective flag **catalogs** when Mode exists (§11).

# 9. Canonical Definition Model

**LOCKED DECISION — smallest valid design:**

Prefer a **lightweight** canonical definition structure — **not** a new platform.

Each definition **may** include: stable key; source (`env` \| `settings`); default; classification; effective-value resolver reference; operator description; legacy/transitional status; Engineering Mode visibility; product visibility (`false` for migration catalogs); runtime owner.

**LOCKED DECISION — location:**

1. **Preferred:** extend `feature_flags.py` with a single `FLAG_DEFINITIONS` (or equivalent) structure that build-info **imports**.  
2. **Allowed:** small adjacent module (e.g. `flag_registry.py`) **only if** needed to avoid circular imports or bloat — must remain thin.  
3. **Forbidden as sole SoT:** hand-maintained build-info capability tuples with independent semantics.

**Must:** eliminate duplicated build-info semantics; avoid circular imports (`feature_flags` must not import `build_info`); no runtime behavior change; testable; no broad refactor.

**Must not introduce:** remote flag service; dynamic rollout platform; DB-driven registry engine; plugin architecture; new event system.
