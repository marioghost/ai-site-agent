# Step 067 — verify-release Root Cause Analysis

**Incident:** standalone `verify-release` reported FAIL after successful Step 067 deploy  
**Deploy tip:** `991081a620369b0af18a63b303d25550bbbc71d2`  
**Deploy report:** `/opt/ai-site-agent/deployments/20260804_090454-991081a.json`  
**Evidence timestamp:** 2026-08-04T15:14:57Z  
**Tooling fixed in this task:** NO

---

## 1. Incident summary

Canonical `deploy full` for Step 067 completed SUCCESS with deploy-time `verify-release=PASS` and `smoke=PASS`. A later standalone `verify-release` run (non-root) reported health and `/api/build` as unreachable. Direct runtime checks, backend journal, and smoke showed the services were healthy. RCA proved a **verification tooling false-negative**, not a product or runtime outage.

---

## 2. Observed sequence

1. Operator ran `sudo bash deploy/manage_deploy.sh deploy full` against tip `991081a`.
2. Deploy-time stages completed: backup → sync → post_sync migrate → restart → health → **verify-release PASS** → **smoke PASS**.
3. Deployment report recorded SUCCESS (`20260804_090454-991081a.json`), duration 34s, `rollback_recommendation=none`.
4. Post-deploy Runtime Validation re-ran smoke → **PASS**.
5. Post-deploy Runtime Validation re-ran standalone `verify-release` → **FAIL** with messages implying health / `/api/build` unreachable.
6. Backend journal at the failure window (`~09:04:54Z`) showed `GET /api/health` and `GET /api/build` returning **200 OK**.
7. Investigation found root-owned fixed temp files under `/tmp/vr-*.json` and reproduced curl write failure exit **23** with HTTP **200**.

This failure is **not** described as a timing race.

---

## 3. Exact root cause

`deploy/lib/verify_release.sh` writes verification payloads to **fixed paths**:

- `/tmp/vr-health.json`
- `/tmp/vr-build.json`
- `/tmp/vr-overview.json`
- `/tmp/vr-qdrant.json`

Deploy-time verification runs under **sudo/root**, creating those files as **root-owned** (typically mode `644`).

A later **non-root** standalone `verify-release` invokes `curl -o` to the same paths. The process cannot overwrite root-owned files. `curl` returns exit code **23** (write error) even when the HTTP response status is **200**.

The script treats any nonzero `curl` exit as failure and reports the endpoint as unreachable — a misclassification of a **local filesystem write error**.

---

## 4. Reproduction evidence

Reproduced after deploy (operator non-root):

```text
curl -o /tmp/vr-health.json ... http://127.0.0.1:8000/api/health
→ curl exit 23, HTTP 200
```

File ownership at reproduction time:

```text
-rw-r--r-- 1 root root ... /tmp/vr-health.json
-rw-r--r-- 1 root root ... /tmp/vr-build.json
-rw-r--r-- 1 root root ... /tmp/vr-qdrant.json
```

Operator: files **not writable**. Same endpoints succeed when written to a non-colliding path (e.g. `/tmp/api-health-accept-review.json`).

---

## 5. curl exit 23 / HTTP 200 distinction

| Observation | Meaning |
|-------------|---------|
| HTTP 200 | Endpoint reachable; response body produced |
| curl exit 23 | Client failed to write the response body to the output file |
| Script message “unreachable” | **Incorrect** — conflates write failure with network/HTTP failure |

Do **not** record endpoints as unreachable for this incident.
