# Release 1.0 — On-call and rollback procedures

**RFC-100 Release 1.0** (Steps 063–067)  
**Accepted baseline:** tree-equivalent of Step 066 limiter remediation tip (`e74d04a…`; deployed revert-tip `cb8bc7f…` acceptable when trees match)

**Public operator entry point:** `bash deploy/manage_deploy.sh <command>`  
Syntax source of truth: `bash deploy/manage_deploy.sh help`

Prefer least-disruptive mitigation first. **Do not** clear Qdrant. **Do not** restore PostgreSQL for routine code rollback. **Do not** use emergency deploy overrides for normal Release 1.0 rollback.

## On-call — frozen operational invariants (do not “fix” by tuning)

Inherited from accepted Steps 063–066:

| Invariant | Operator expectation |
|-----------|---------------------|
| Ask API | Executive-only entry (Step 064); `KNOWLEDGE_OS_EXECUTIVE_ENABLED=false` → controlled 503 / SSE `executive_disabled` |
| AdmissionGate | single chat domain (`kos_limiter_chat_domain_id=1`); default limit 20; overload → HTTP 429 (not 5xx storm) |
| Maintenance | `MAINTENANCE_INVESTIGATIONS_PER_CYCLE` defaults to 0; execution gated by env |
| Legacy KP / doc-type flags | default OFF |
| DB / Qdrant | no wipe/restore for feature rollback |

AdmissionGate metrics (process-local): `kos_limiter_chat_domain_id`, `kos_limiter_chat_limit`, `kos_limiter_chat_active`, `kos_limiter_chat_timeout_total`.

## Level 1 — Operational kill-switches (preferred)

Use when behaviour must be constrained without code rollback:

| Switch | Effect |
|--------|--------|
| `KNOWLEDGE_OS_EXECUTIVE_ENABLED=false` | Hard controlled unavailable for Ask |
| `REASONING_SERVICE_ENABLED=false` | Reasoning path off (Executive remains entry) |
| `MAINTENANCE_EXECUTION_ENABLED=false` | Skip maintenance execution |
| `MAINTENANCE_INVESTIGATIONS_PER_CYCLE=0` | Budget hard-stop |

Restart backend after env changes. Re-check `health` and `/api/build`.

---

## Level 2 — Code rollback (known-good `origin/main`)

`deploy/manage_deploy.sh` **does not** accept an arbitrary prior commit. Rollback means placing a **known-good published tip on `origin/main`**, then using the canonical deploy chain.

### Rollback targets (examples)

| Class | Target |
|-------|--------|
| Pre-closure Release 1.0 metadata only | revert Step 067 closure commit(s) |
| Last accepted Step 066 runtime tree | tree of `e74d04a…` (may be revert-tip `cb8bc7f…`) |
| Parent DB-session remediation tree | `4f89d13…` (tree match; emergency only with authorization) |

Preferred git path: approved **revert** advancing `origin/main` without force-push.

### Canonical deploy

```bash
sudo bash deploy/manage_deploy.sh deploy full
```

`deploy full` owns backup, migrate decision, restart, health, in-deploy verify-release, smoke, and deployment report.

### Post-rollback verification

Record: `origin/main`, build-info, frontend, `/api/build`, health, migration version, lifecycle fields.

**Do not** restore PostgreSQL or Qdrant for normal code rollback.

---

## Explicit non-rollback actions

- Do **not** delete Epistemic Memory rows to undo Release 1.0.
- Do **not** clear Qdrant or force reindex for feature rollback.
- Do **not** increase chat/LLM limits or pool size to mask overload.
- Do **not** reopen Step 066 load/restart/rollback evidence as part of incident response.
- Do **not** flip `staging_validated` / `production_ready` from this runbook alone.
