## 1. Purpose

### 1.1 Why this document exists

The Master Inventory lists **what** Product Completion must absorb. Without an execution constitution, implementers re-open settled questions:

- Should this move or be rewritten?
- Where does it belong?
- Can this land before that?
- May we keep a temporary second home?

This Execution Strategy answers those questions **once**, for every inventory cluster.

### 1.2 Document roles (do not conflate)

| Document | Owns | Does not own |
|----------|------|--------------|
| **Master Inventory** | Complete set of findings, clusters, conflicts, effort bands | How to execute; order; dates |
| **This Execution Strategy** | Rules, ownership finality, dependency graph, migration philosophy, acceptance/DoD, forbidden work | New inventory items; roadmap; UI design; priorities |
| **Implementation** (future) | Code/docs changes that obey this strategy and close inventory items | Changing ownership or inventing scope |
| **Roadmap** (future, if any) | Sequencing and milestones | Redefining ownership or inventory |

**Inventory is immutable for scope.** This strategy is immutable for **execution law** once accepted. Implementation and any later roadmap must obey both.

### 1.3 Relationship to RFC-101 / RFC-102 / Product Readiness

| Authority | Role during Product Completion |
|-----------|--------------------------------|
| RFC-101 | Final product IA, routes, Screen Contracts, terminology, ownership matrices |
| RFC-102 | Final frontend structure (folders, state, shared UI, guards) |
| Product Readiness | Gate, debt policy, Accepted Product criteria |
| This strategy | How clusters may touch the codebase without violating the above |

If an implementation proposal conflicts with RFC-101 product decisions, **RFC-101 wins**. If it conflicts with RFC-102 structure, **RFC-102 wins**. If it conflicts with this strategy’s migration/ownership rules, **this strategy wins** over ad-hoc convenience. This strategy **must not** redefine RFC-101 product IA.

## 2. Execution Principles

These principles are normative.

### P1 — Single Source of Truth

For each concern there is exactly one authoritative owner document and one owner screen (or Engineering Mode destination). Inventory duplicates are **labels for the same outcome**, not permission to implement twice.

### P2 — No duplicate ownership

At program end (and at each cluster DoD), no two product surfaces may own the same user job. Secondary deep-links are allowed; second owners are forbidden.

### P3 — Move instead of rewrite

Existing capabilities that already work must be **relocated and re-homed** under RFC-101 ownership. Do not rebuild backend powers or invent parallel UIs “while migrating.” Rewrite UI chrome only when required to meet Screen Contracts—not to recreate capability.

### P4 — Incremental migration

Clusters execute as incremental migrations. Coexistence of legacy route and canonical route is allowed **temporarily** under §6. Big-bang replacement of the entire Dashboard in one change is forbidden.

### P5 — No big-bang rewrite

RFC-102 “migrate on touch” remains valid **inside** a cluster’s owning scope. Crossing cluster ownership mid-flight without completing move rules is forbidden. Program-wide rewrite of all pages in one PR is forbidden.

### P6 — Every screen has one owner

RFC-101 Screen Contracts and Feature Ownership Matrix are final. Clusters may not create alternate screens for the same job.

### P7 — Every capability has one owner

RFC-101 Product Capability Matrix / One-Place Register are final. Engineering Mode **reveals** capabilities; it does not create a second product owner for the same capability.

### P8 — Engineering Mode isolates complexity

Default product (Mode off) must satisfy Product Readiness simplicity. Engineering complexity lives under `/engineering/*` (and Ask progressive disclosure only as RFC-101 already allows). Hidden eng pages outside Engineering Mode are forbidden.

### P9 — Product simplicity first

When eng convenience conflicts with product simplicity, **product wins**. Density that violates Home/Ask/Settings contracts must be redistributed, not preserved as “operator preference” in the default product.

### P10 — Architecture before cosmetics

IA, ownership, isolation, redirects, and structure land before visual polish that does not change ownership. Cosmetics alone do not close inventory items that require ownership moves.

### P11 — Integrate; never strip RFC-100 capability

Simplification must not delete Release 1.0 engineering capabilities. Move to Engineering Mode or product language; do not remove.

### P12 — Frozen engineering boundary

Product Completion must not reopen RFC-100, Step 067, or Release 1.0 engineering closure metadata semantics as a vehicle for product work. Ops gates (`staging_validated`, `production_ready`) are out of scope unless a separate ops program authorizes them.

## 3. Execution Rules

Immutable. Violations reject the cluster.

### R1 — No new ownership

A cluster cannot invent a new owner screen, nav family, or capability home beyond RFC-101 / inventory.

### R2 — No renaming outside RFC-101 glossary

A cluster cannot introduce product labels that conflict with RFC-101 §17. Legacy names may exist only as redirects or temporary aliases during migration.

### R3 — No parallel navigation

A cluster cannot leave two top-level (or dual-label) entries for one job after its DoD. During migration, dual entries are allowed only under §6 coexistence rules and must be removed at cluster close.

### R4 — No lifecycle mutation

A cluster cannot change Release 1.0 engineering closure fields, reopen Step 067, or redefine LIFECYCLE states. Clarifying docs (G12) may explain dual meaning of engineering `accepted` vs Product Accepted Product without altering frozen engineering records.

### R5 — No route redefinition

Canonical routes in RFC-101 §6 are final. Clusters implement them; they do not invent alternate canonical paths. Legacy paths become redirects only.

### R6 — Move once

Functionality moves to its final owner **once**. A cluster may not park capability in an intermediate “temporary home” that is neither legacy nor final RFC-101 owner. Temporary coexistence means legacy + final, not legacy + intermediate + final.

### R7 — No product Settings as eng dump

Retrieval knobs, system prompt encyclopedia, flag catalogs, and migration matrices must not remain in default product Settings after the Settings/Eng clusters that own those moves complete. Destination is Engineering Advanced / Build & flags per inventory.

### R8 — Diagnostics leave Ask only into Engineering

Ask productization must not delete diagnostics. It must move them to `/engineering/ask-details` (or the inventory Eng destination). Therefore Ask cannot complete isolation before Engineering Mode provides that destination (see §4–§5).

### R9 — Home cannot empty without receivers

Home readiness must not delete Overview widgets that still have no Insights or Engineering owner. Redistribution targets must exist (or be created in the same atomic change set that removes them from Home).

### R10 — G11 is not Dashboard scope

Backend deferred non-product items (inventory G11) are **out of Product Completion Dashboard clusters**. They must not be bundled into Dashboard PRs “while we are here,” and must not block Dashboard cluster acceptance.

### R11 — G10 is independent tooling

verify-release hygiene does not unlock or block UI ownership. It must not be used as a pretext to change deploy architecture.

### R12 — Gate is mandatory for product-facing clusters

Clusters that change user-facing Dashboard surfaces must record Product Readiness Gate results per RFC-PRODUCT-READINESS. “Compiles” is insufficient.

### R13 — RFC-102 structure for new and migrated screens

New canonical screens and migrated owners must land in RFC-102 feature modules (or complete migrate-on-touch into them). Growing legacy `pages/` monoliths as the permanent home of RFC-101 screens is forbidden.

### R14 — No ops Dashboard pages

No cluster may add a product Dashboard “ops load,” deploy console, or Prometheus console. Observation remains APIs/docs/Eng status as already constrained.

### R15 — Inventory closure required

A cluster is not done until corresponding inventory findings it claimed are marked closed in the program’s inventory tracking (without deleting inventory history). Closing means evidence of completion, not removing the finding text from the Master Inventory document.

### 4.4 Circular-dependency resolution (final)

**Settings General ↔ Engineering Mode:**  
RFC-101 assigns the Mode toggle to **Settings → General**. Therefore:

- G2 may not invent a toggle elsewhere.
- G7 need not be **fully** complete before G2 starts.
- A **General** owning surface (canonical `/settings/general`, even if other Settings children still legacy) **must exist** before Mode can be considered implemented.
- That General surface is the **first owning slice of G7**, not a third settings home.

**Ask ↔ Engineering Mode:**  
Ask may adopt `/ask` naming/routing only if eng diagnostics remain reachable. Ask **isolation DoD** (diagnostics removed from default Ask) requires G2 ask-details destination populated (move, not delete).

**Home ↔ Insights/Eng:**  
Home DoD requires every removed Overview capability to have a living owner in Insights or Engineering.

### 4.5 What “independent” means

Independent = may execute without waiting on Dashboard cluster completion. Independent does **not** mean exempt from Gate, RFC-101, or this strategy when it touches product UI (G10/G12 normally do not).

## 6. Migration Philosophy

### 6.1 Coexistence

- Legacy route and canonical route **may** coexist temporarily.
- During coexistence, **one owner screen** is designated final; legacy is alias/redirect or explicitly deprecated shell.
- Coexistence ends when the owning cluster reaches DoD.

### 6.2 Single final owner

- At cluster DoD, exactly one owner remains for each job/capability the cluster claimed.
- Deep-links to the owner are allowed; duplicate owners are not.

### 6.3 Redirects mandatory

- Every removed or renamed legacy path listed in RFC-101 §12 that this program touches **must** redirect to the canonical target.
- Catch-all must not revive Overview as permanent home after Home exists.

### 6.4 Move, then delete

- Move capability to final owner.
- Remove from legacy mount points.
- Delete obsolete components, dead imports, and unused translations for that capability in the **same cluster close** (or an immediately following cleanup change that does not reopen ownership).
- Leaving “just in case” duplicates is forbidden after DoD.

### 6.5 Feature flags

- Feature flags for Dashboard migration are allowed **only** when required for safe incremental cutover of a specific surface.
- Flags must not create a permanent second product.
- Flags are not a substitute for redirects or ownership clarity.
- Migration flags must not reappear in product Settings catalogs.

### 6.6 Structure migration

- When a screen is migrated, place it under RFC-102 feature ownership.
- Do not copy business UI into a new route while leaving the old monolith permanently mounted.

### 6.7 i18n

- Glossary terms update with ownership moves.
- Stale legacy keys for removed nav labels must be removed or clearly unused at cluster DoD.
- en/uk must not diverge in product terminology for the same route.

### 6.8 Tests

- Ownership/source-contract tests that asserted “no Engineering Mode” during RFC-100 are **historical constraints for that era**. Product Completion **must** replace them with tests that assert Mode isolation and canonical routes—without reopening RFC-100 step packages.

## 7. Acceptance Rules

Every future Product Completion cluster must satisfy all applicable rows before acceptance.

### 7.1 Architecture

- Obeys RFC-101 ownership and routes.
- Obeys RFC-102 structure for migrated/new screens.
- Obeys this strategy’s dependency and move-once rules.
- No new ownership, no parallel nav at DoD.

### 7.2 UX / Product Readiness

- Product Readiness Gate recorded for user-facing changes.
- No eng concepts in default product chrome beyond RFC-101 allowances.
- Screen Contracts: primary CTA, empty/loading/error addressed for touched screens.
- No “experimental / engineers only / ignore this” dependence in default product.

### 7.3 Code

- No duplicate mounts of moved widgets.
- No orphan components introduced; obsolete ones removed or filed under Eng with a single import path.
- No dead imports for removed surfaces.
- No growth of forbidden top-level module nav.

### 7.4 Documentation

- Cluster note or equivalent records what moved where.
- Ownership matrices not contradicted.
- Inventory items claimed by the cluster marked closed in program tracking.
- G12 clarifications used where engineering vs product acceptance language appears.

### 7.5 Tests

- Relevant automated tests green.
- Nav/route ownership assertions updated to RFC-101 truth.
- No failing historical “absence of Eng Mode” tests left as false authority.

### 7.6 Hygiene checklist (mandatory at DoD)

| No duplicate navigation for claimed jobs | Yes |
| No stale routes without redirect | Yes |
| No stale product translations for removed labels | Yes |
| No dead imports for removed mounts | Yes |

## 8. Definition of Done (cluster)

A cluster is **complete** only when all of the following are true for its claimed inventory scope:

1. **Ownership final** — one owner per claimed job/capability.  
2. **Routes final** — canonical routes live; legacy redirected.  
3. **Product Mode off** — default chrome free of eng dumps the cluster was responsible for moving.  
4. **Engineering Mode** — if the cluster moved eng content, that content is reachable under Eng when Mode on.  
5. **No duplicates** — §7.6 checklist pass.  
6. **Structure** — migrated screens under RFC-102 ownership pattern.  
7. **Tests green** — including updated ownership tests.  
8. **Docs/Gate** — Gate recorded where required; cluster documentation updated.  
9. **Inventory closure** — corresponding inventory findings closed in program tracking (history preserved).  
10. **No lifecycle breach** — RFC-100 / Step 067 / engineering closure untouched.

Compiling, “looks better,” or partial rename **without** ownership finality is **not** Done.

## 10. Success Criteria

Success is defined **without** dates, roadmaps, or implementation narratives.

RFC-101 Product Completion has succeeded when:

1. **Default product IA** matches RFC-101: Home · Knowledge · Ask · Insights · Settings only at top level (Mode off).  
2. **Engineering Mode** exists, default off, isolates inventoried eng surfaces under `/engineering/*`.  
3. **Every inventoried product job** has a single owner screen satisfying its Screen Contract.  
4. **No duplicate navigation or dual labels** remain for one job.  
5. **Legacy routes redirect**; Overview/Chat Test/Indexing/Sources/etc. are not permanent homes.  
6. **Settings** are split per RFC-101; eng knobs/prompt/flag catalogs are not in default product Settings.  
7. **Ask** is a product Q&A surface; diagnostics live in Eng ask-details.  
8. **Home** expresses readiness + next action—not an eng status wall.  
9. **RFC-102 structure** holds for product/eng feature modules (no permanent legacy monolith owners).  
10. **Product Readiness Program criteria** for Accepted Product are satisfiable: Gate discipline applied, no open must-resolve product debt of the classes Product Readiness defines for acceptance, cold-demo possible without coaching.  
11. **RFC-100 engineering closure remains intact**; ops gates unchanged unless separately authorized.  
12. **Master Inventory findings** claimed by the program are closed; no unresolved duplicate-ownership conflicts from Part B remain in the product.

Success is **not**: a prettier legacy console, a partial rename, or engineering metadata alone.

## 11. Conflict resolutions (inventory Part B → final law)

These inventory conflicts are **closed** by this strategy:

| Inventory conflict | Final resolution |
|--------------------|------------------|
| `accepted=1.0` vs Product Accepted Product | Dual meaning: engineering closure metadata remains frozen; Product Accepted Product requires this program’s success criteria. G12 may document; clusters must not “fix” metadata by rewriting Step 067. |
| Step-local Gate PASS vs program incomplete | Past step Gates remain historical for RFC-100. Product Completion requires Gate on **product surfaces it changes**. |
| Prior audit “CLOSURE PREMATURE” vs frozen RFC-100 complete | RFC-100/067 frozen complete; remainder is Product Completion only. Do not reopen engineering closure. |
| verify-release standalone vs product work | Tooling defect (G10); non-blocking for UI ownership; optional independent fix. |
| Dense Overview/Chat vs simplicity | Product simplicity wins; redistribute via G5/G2/G3/G6 rules. |
| Eng Mode vs Settings completeness | General slice required for toggle; full Settings split not required before Mode shell. |
| Ask rename vs diagnostics | Rename/routing may proceed with coexistence; isolation DoD requires Eng ask-details move. |
