| Layer | In Step 052? | Notes |

### 2.2 Distinctions

| Concern | Step 052 | Later |
|---------|----------|-------|
| API contract removal | Yes | — |
| Internal compatibility (ORM + scorer still read columns) | Yes, keep | Optional freeze to constants |
| Database cleanup (`DROP COLUMN`) | No | Release 1.0 / dedicated cleanup — **REQUIRES ADR** if proposed early |
| Behavior change (flags-OFF chat ranking) | **Must not** | Only if values diverge from defaults or constants change |

### 2.3 Recommended smallest architecture-safe scope

**PROPOSED MINIMAL INTERPRETATION — Option A (refined):**

1. Remove from `SettingsRead` / `SettingsUpdate` / `_to_read` / `update_settings` mapping:  
   `title_match_boost`, `heading_match_boost`, `homepage_boost_enabled`, `homepage_boost_value`, `short_query_lexical_boost`.
2. Keep ORM columns and current runtime readers (`DocumentScorer`, RPS inject, cache NS hash).
3. Leave dashboard removal to **Step 053** (title/heading controls) plus types/i18n cleanup for the five fields.
4. Do **not** drop DB columns; do **not** move behavior into Reasoning / Evidence Assembly; do **not** invent new boost abstractions.
5. Do **not** include `ranking_freshness_weight` or KP `boosted_*` lists.

## 6. Migration options

| Option | Description | Behavior risk | Rollback | DB | API | Dashboard | Tests | Sequencing |
|--------|-------------|---------------|----------|----|-----|-----------|-------|------------|
| **A** | Remove from public Settings API only; keep DB + runtime reads | **Lowest** (defaults live) | Code revert | No migration | Breaking GET shape for admin clients | Still shows title/heading until 053 | Schema/API tests | **052 then 053** |
| **B** | A + stop internal runtime reads (hardcode constants) | Medium — must prove parity | Code revert | Columns remain | Same as A | 053 | Scorer/golden parity critical | Larger than RFC title |
| **C** | Full removal including `DROP COLUMN` | High for rollback | Migration downgrade fragile | Migration required | Same | 053 | Migration tests | **Not for 052** |
| **D** | Deprecate in API (keep fields, mark deprecated) then remove later | Lowest short-term | N/A | No | Soft | Soft | Docs | Delays RFC 052 intent |

### Recommendation

**Option A (refined)** — **GO** for Step 052 implementation after review approval.

Rationale:

- Matches RFC title (“Settings API response”).
- Live values are defaults → ranking unchanged if ORM/scorer keep reading columns.
- `SettingsUpdate` already uses `extra="ignore"` → old dashboards sending removed fields will not 422.
- Leaves Step 053 for UI; leaves DB drop for a later ADR.
- Avoids Reasoning/EA ownership creep.
